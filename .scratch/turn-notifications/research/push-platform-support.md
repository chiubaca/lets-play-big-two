# Push platform support (primary-source check, 27 September 2026)

## Recommended delivery path

**Verified:** Use standards-based Web Push first: a same-origin service worker, user-initiated notification permission, `PushManager.subscribe({ userVisibleOnly: true, applicationServerKey: VAPID_PUBLIC_KEY })`, and a server that stores each device's `endpoint`/`p256dh`/`auth` and sends encrypted Web Push requests to that endpoint with VAPID credentials. On `push`, call `registration.showNotification()`; on `notificationclick`, focus/navigate an existing client or `clients.openWindow()` to a same-origin game URL. Cloudflare documents this flow on Workers/Agents, including pruning 404/410 subscriptions; Chrome explicitly says VAPID + Web Push protocol works with its FCM-hosted **push endpoint without a Firebase project, FCM SDK, or FCM API credentials**. FCM's _web SDK/token + FCM HTTP API_ is an optional, different integration, not a prerequisite for Chrome Web Push. [Cloudflare](https://developers.cloudflare.com/agents/communication-channels/webhooks/push-notifications/) · [Chrome: Web Push interoperability](https://developer.chrome.com/blog/web-push-interop-wins) · [Firebase: web SDK](https://firebase.google.com/docs/cloud-messaging/js/client)

**Important distinction:** Bubblewrap wraps an _existing_ PWA for Android distribution; it does not replace Web Push with native Firebase Cloud Messaging. Native FCM device tokens / Android SDK are a separate implementation if a native channel is later chosen. Firebase's web documentation instead configures VAPID and a service worker to retrieve an FCM **web registration token**; do not conflate that token or API with a raw `PushSubscription` endpoint. [Bubblewrap quick start](https://developer.chrome.com/docs/android/trusted-web-activity/quick-start) · [Firebase web setup](https://firebase.google.com/docs/cloud-messaging/js/client) · [Chrome](https://developer.chrome.com/blog/web-push-interop-wins)

**2026 nuance:** Apple also offers _Declarative Web Push_ (iOS/iPadOS 18.4, macOS Safari 18.5), which can display a notification without service-worker execution. It does **not** remove the value of the classic service-worker flow for one cross-browser implementation; evaluate it separately if Apple-only reliability/energy behavior becomes important. [WebKit](https://webkit.org/blog/16535/meet-declarative-web-push/) · [WebKit macOS release](https://webkit.org/blog/16563/webkit-features-in-safari-18-5/)

## Registration, navigation, and fallbacks

- Register a root-scoped worker on the **frontend HTTPS origin** (not a distinct API origin); check `serviceWorker`, `PushManager`, `Notification`, `Notification.permission`, then use the active registration's `pushManager.getSubscription()` before subscribing. Expose only the VAPID **public** key to clients; keep the private key on the server. Resync on login/device changes, unsubscribe/logout, and remove expired/revoked endpoints (404/410). Root worker placement simplifies scope; service workers require HTTPS or localhost. [Chrome scope/lifecycle](https://developer.chrome.com/docs/workbox/service-worker-lifecycle) · [Cloudflare](https://developers.cloudflare.com/agents/communication-channels/webhooks/push-notifications/) · [Edge](https://learn.microsoft.com/en-us/microsoft-edge/progressive-web-apps/how-to/push)
- Store a server-authenticated subscription **per device/browser/install**, never assume one subscription per user. Push is opt-in and user-visible, not guaranteed delivery or a replacement for the existing live connection. Retain the live room UI for connected users; provide an install explanation on iOS and a settings/unsubscribe route when permission is denied. Apple requires user-visible notification for classic push; Chrome can revoke permissions for abusive/inactive sites. [Cloudflare](https://developers.cloudflare.com/agents/communication-channels/webhooks/push-notifications/) · [WebKit](https://webkit.org/blog/12945/meet-web-push/) · [Chrome policy](https://developer.chrome.com/blog/web-push-rate-limits)
- Put a **same-origin, in-scope, allowlisted** room path or opaque room identifier in notification `data` (not an arbitrary supplied URL); `notificationclick` should `waitUntil` an existing client's `navigate(target)`/`focus()` or `clients.openWindow(target)`. The app route must handle auth re-entry and unavailable rooms. This is a recommended application design, not a platform-guaranteed cross-OS app-launch behavior. [Chrome notification click](https://developer.chrome.com/blog/push-notifications-on-the-open-web) · [MDN API background: openWindow](https://developer.mozilla.org/en-US/docs/Web/API/Clients/openWindow)
- For **external Android HTTPS links** to open the TWA, Bubblewrap generates a `VIEW` intent filter with `autoVerify`; host `/.well-known/assetlinks.json` containing the correct app package and **installed/Play signing certificate**. Browser TWA verification also depends on Digital Asset Links and falls back to a Custom Tab if it fails. Keep target URL on a verified origin/in the intended app scope; test cold/warm notification taps separately from external links, as they are not the same launch mechanism. [Bubblewrap template](https://github.com/GoogleChromeLabs/bubblewrap/blob/main/packages/core/template_project/app/src/main/AndroidManifest.xml) · [Chrome quick start](https://developer.chrome.com/docs/android/trusted-web-activity/quick-start) · [Android App Links](https://developer.android.com/training/app-links/verify-applinks)

## Test gates / open questions

1. **Real HTTPS and real send:** localhost is an exception for service-worker development, but a desktop DevTools **Push** button only emulates a payload-less event; it does not prove subscription creation, VAPID encryption, endpoint reachability, delivery, OS permission or tap routing. Test a real send to each returned endpoint, including after tabs close, denial/revocation, reinstallation, multiple devices and 404/410 cleanup. [Chrome lifecycle](https://developer.chrome.com/docs/workbox/service-worker-lifecycle) · [Chrome DevTools](https://developer.chrome.com/docs/devtools/progressive-web-apps) · [Cloudflare](https://developers.cloudflare.com/agents/communication-channels/webhooks/push-notifications/)
2. **iOS:** test a real Home Screen installation and explicit in-app tap/permission flow on iOS 16.4+; an open Safari tab, desktop responsive emulation or bookmark does not validate this path. WebKit says Xcode simulators can test Home Screen app UI, **but whether a given simulator/environment can complete production APNs Web Push delivery is not established by these sources**: gate actual receipt and notification-tap routing on a physical iPhone/iPad. For auth testing, WebKit says browser cookies are copied into a new Home Screen app only starting iOS 17.2, and non-cookie storage is not copied; do not rely on an existing browser login surviving install. [WebKit push](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/) · [WebKit simulator UI](https://webkit.org/blog/14445/webkit-features-in-safari-17-0/) · [WebKit install cookies](https://webkit.org/blog/14787/webkit-features-in-safari-17-2/)
3. **TWA:** build with notification delegation enabled; inspect final merged manifest for `POST_NOTIFICATIONS`, service/activity, and Digital Asset Links for **both sideload and Play signing keys**. On an Android 13+ fresh install test OS Allow/Deny, browser permission, notification attribution, cold/warm click and external App Link. Android publishes ADB commands to reset permission flags without resetting the phone. **Uncertain until device-tested:** whether the chosen Bubblewrap/browser/OS combination correctly maps the web prompt to the wrapper prompt and opens notification targets in the intended TWA. The upstream helper contains a native permission-request activity, but this is not a cross-device delivery guarantee. [Android permission and ADB cases](https://developer.android.com/develop/ui/views/notifications/notification-permission) · [Bubblewrap template](https://github.com/GoogleChromeLabs/bubblewrap/blob/main/packages/core/template_project/app/src/main/AndroidManifest.xml) · [Bubblewrap historical fix](https://github.com/GoogleChromeLabs/bubblewrap/pull/731) · [Chrome signing/verification](https://developer.chrome.com/docs/android/trusted-web-activity/quick-start)

## This repository (source inspection, not device verification)

- The production frontend already links [`manifest.webmanifest`](../../../apps/frontend-web/public/manifest.webmanifest) (`id: "/"`, `display: "standalone"`, `scope: "/"`) and registers the root-scoped [`service-worker.js`](../../../apps/frontend-web/public/service-worker.js) from [`__root.tsx`](../../../apps/frontend-web/src/routes/__root.tsx). The worker currently caches offline assets and navigations only; it has no `push` or `notificationclick` listeners. Extend **this worker**, not a second one for the same scope. The backend runs as a separate Cloudflare Worker/API origin with `nodejs_compat` ([`wrangler.jsonc`](../../../apps/backend/wrangler.jsonc)); there are no push credentials or subscriptions in the inspected backend. Its choice of subscription storage, fan-out and retries belongs to [Decide subscription storage and reliable turn delivery](../issues/06-delivery-design.md), not this ticket.
- The Android package is a Bubblewrap TWA for `https://big-two.chiubaca.com/`, targeting API 36 ([`twa-manifest.json`](../../../apps/android/twa-manifest.json), [`app/build.gradle`](../../../apps/android/app/build.gradle)). `enableNotifications` is currently **false** in both; generated [`AndroidManifest.xml`](../../../apps/android/app/src/main/AndroidManifest.xml) has a `DelegationService` but disables it via that flag. The existing merged release manifest contains **no** `POST_NOTIFICATIONS` declaration. This is evidence about the _current build_, not a prediction about a regenerated one. Plan an Android wrapper update, regenerate with the pinned Bubblewrap flow ([`README`](../../../apps/android/README.md), [`update-android.sh`](../../../scripts/update-android.sh)), inspect the resulting manifest and verify a Play-installed build on Android 13+. Do not assume a web-only deploy enables TWA notification attribution or native permission.
- The generated app already has an HTTPS `VIEW` intent filter for its host ([`AndroidManifest.xml`](../../../apps/android/app/src/main/AndroidManifest.xml)); the frontend has [`assetlinks.json`](../../../apps/frontend-web/public/.well-known/assetlinks.json) with upload and Play signing fingerprints. The direct room route is `/room/$roomId` ([`$roomId.tsx`](../../../apps/frontend-web/src/routes/room/$roomId.tsx)); it asks signed-out visitors to sign in, then fetches room state, and displays an error if the room no longer exists ([`online-game-room.tsx`](../../../apps/frontend-web/src/components/game-room/online-game-room.tsx)). Use a validated `/room/<id>` URL for clicks; test browser/PWA/TWA opening and auth re-entry rather than presuming an Android App Link proves notification-click handling.
- The [Play release sheet](../../../apps/android/PLAY_STORE_RELEASE.md) says a Play-installed build has not yet been verified on-device. Until an end-to-end device check succeeds, treat Android TWA notifications as a **conditional supported path**, not a guaranteed capability. Inability to grant permission or deliver should leave the account-wide setting clearly unavailable on that device and the existing live room UX intact; do not silently substitute native FCM or claim delivery is guaranteed. The detailed disabled/denied UI and account/device opt-in semantics are for [Decide the online Table settings opt-in flow](../issues/04-settings-and-permission.md).

**Scope limit:** This is platform research and local source inspection only; neither the production deployment nor physical-device delivery has been tested here. No push implementation or game-behavior decision is made in this note.
