# Turn delivery design research (28 September 2026)

**Scope:** planning, not implementation or device verification. The existing decisions require one alert per device per distinct successful turn, only if the seated Player was away at turn start, account-wide default-off consent plus explicit per-install enrollment, generic text, and original-account-only click routing ([map](../map.md), [turns](../issues/02-turn-boundaries.md), [presence](../issues/03-away-presence.md), [settings](../issues/04-settings-and-permission.md), [return](../issues/05-alert-content-and-return.md)). The chosen transport is standards-based Web Push ([platform study](push-platform-support.md)).

## Existing seams and competing placements

- D1 already owns `user`, `session`, `accountDeletion`, `room`, and `usersToRooms`; room game state is private SQLite in `BigTwoRoomObject`. The authenticated HTTP action route calls `gameAction`; that method validates the action, commits a snapshot, broadcasts it, and returns success. The machine advances on deal, play, pass, including a final pass to a new lead, and has reset/end paths. Neither room broadcasts nor `usersToRooms` are a trustworthy new-turn event or proof of current seat. [schema](../../../packages/data-ops/src/drizzle/schema.ts) · [auth schema](../../../packages/data-ops/src/drizzle/auth-schema.ts) · [route](../../../apps/backend/src/hono/app.ts) · [DO](../../../apps/backend/src/do/big-two-room-do.ts) · [machine](../../../packages/game-state-machine/src/game-state-machine.ts)
- **Recommend D1 for account consent and per-install registrations**, indexed by user; D1 is already the account database and supports atomic _D1-only_ batches. One row per user defaults to off (absence = off); one row per subscription with unique endpoint hash/unique endpoint, user ID, originating session ID, endpoint, `p256dh`, `auth`, generation and timestamps. Endpoint is a sensitive capability URL; avoid exposing it in logs or GET responses. Do not put subscriptions into each room DO (requires cross-room updates on off/sign-out) or put account consent into a single room. A per-user DO is plausible but introduces a new namespace plus D1/auth coordination without simplifying game-state atomicity. [D1 API](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch) · [DO storage scope](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/) · [Push API security](https://www.w3.org/TR/push-api/#security-and-privacy-considerations) · [local schema](../../../packages/data-ops/src/drizzle/schema.ts)
- Enrollment/unenrollment/settings APIs should require the current authenticated account, reject `accountDeletion`, validate HTTPS push-service endpoint against an explicit approved provider host policy (avoid arbitrary server-side POST/SSRF), limit key/URL sizes, and use D1 conditional writes so a concurrent off/deletion cannot recreate a row. Make the endpoint globally unique and **never silently reassign it** between accounts: if a different account owns this origin-level subscription, detach/revoke and require an explicit new enrollment tap. Store a session binding to make sign-out or session revocation immediately fail eligibility even if cleanup is delayed. Consent-off removes all that user's rows and increments a consent generation; re-on does not restore rows. These are design controls, not current features. ## Authoritative event, presence, fan-out

1. **At `gameAction` inside the room DO**, compare accepted pre/post snapshots and event type, not state broadcasts: only `START_GAME` into play, accepted plays/passes into ongoing play create a turn; winner/reset/leave terminates one. Persist a monotonically increasing room-local turn sequence (and game/deal generation or equivalent) plus `{turnId, playerId}` on the game record. Advance even if the same player leads a new round; never advance on an invalid/no-op event. Store a bounded outbox intent for an away-at-start turn **in the same room SQLite transaction** as the snapshot/turn ID, using `transactionSync`; if the game write fails the action fails, but a later push/network/D1 lookup failure must not turn an already committed action into an error. Check room-local fresh affirmative presence at transition time; if active, record no delivery intent and never requeue that turn. [local gameAction](../../../apps/backend/src/do/big-two-room-do.ts) · [machine](../../../packages/game-state-machine/src/game-state-machine.ts) · [DO SQL transaction API](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/#transactionsync) · [presence decision](../issues/03-away-presence.md)
2. **Presence belongs with the room DO**, keyed by authenticated `{playerId, tab/window token}` rather than the existing socket count. A visible AND focused room view announces/renews an affirmative lease (e.g. 15–30-second heartbeat and short expiry); blur/hidden/leave clears promptly, expiry handles abrupt disconnect. Authenticate updates in HTTP (session + room) before trusting them in DO; `visibilityState`/`hasFocus()` from that client are advisory, not a proof against a malicious client. Read fresh leases at turn start, immediately before each send, and in a narrowly scoped, no-store recipient-check endpoint at SW receipt; absent/expired evidence means away. The current game WebSocket is read-only and attachment proves a valid session, **not focus**. [DO socket implementation](../../../apps/backend/src/do/big-two-room-do.ts) · [client socket](../../../apps/frontend-web/src/routes/room/-subscribe-to-game-state.ts) · [presence decision](../issues/03-away-presence.md)
3. **Dispatch with the room DO alarm and durable outbox**, not an unawaited promise, request-scoped `waitUntil`, or an enqueue in D1 after the DO commit: the latter can lose an event across two independent databases. After commit, schedule an immediate alarm; alarm drains bounded work, reloads the current turn/room availability and presence, looks up live consent + session-bound subscriptions in D1, and records per-`{turnId, subscriptionId/generation}` progress/retries. Capture the turn's creation time and require that consent and device enrollment both predate it: turning on/enrolling mid-turn must not retroactively issue an alert. Treat cross-database ordering near a simultaneous setting/turn change as an explicit race; off always wins at final send check. On failure, reschedule with bounded backoff and a short absolute deadline; retire stale intents, cap attempts, and retain small sent/terminal markers until the turn expires. Since an alarm is single-slot and at-least-once with only six automatic retries, explicitly reschedule remaining work and provide a periodic **repair sweep** over D1's room index to wake stranded room DO outboxes if scheduling fails after commit. Repair only wakes persisted intents; it must not manufacture alerts from snapshots. Existing cron sweeps room expiry every minute, but currently has no delivery repair. [alarms](https://developers.cloudflare.com/durable-objects/api/alarms/) · [waitUntil limits](https://developers.cloudflare.com/workers/runtime-apis/context/#waituntil) · [local cron](../../../apps/backend/src/index.ts) · [expiry sweep](../../../apps/backend/src/lib/room-expiry.ts) · [settings decision](../issues/04-settings-and-permission.md)
4. Before each POST recheck current room turn, non-expiring room, current seated recipient, absence of active-room presence, on consent, active subscription generation and originating session (and no deletion marker); serialize/guard the **claim** in the room DO, but recheck after any awaited D1/network operation because other actions may interleave. Set a short Web Push TTL and bounded retry window; 2xx means **accepted by push service**, not displayed on the device. On 404/410 delete only the matching subscription generation; retry timeouts/429/5xx with backoff/`Retry-After` where available; do not retry permanent bad credentials/config indefinitely. Never log payload, endpoint or encryption keys. [RFC 8030 §§5, 5.2, 7.4](https://www.rfc-editor.org/rfc/rfc8030#section-5) · [Cloudflare push example](https://developers.cloudflare.com/agents/communication-channels/webhooks/push-notifications/#production-considerations) · [DO concurrency/storage](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/)

**Idempotency limit:** Unique outbox/recipient keys prevent duplicate _logical_ work, but a lost HTTP response after a successful send makes network exactly-once impossible. Use the stable turn ID as a device-side dedupe key in persistent service-worker storage (mark before `showNotification`, accept possible missed alert if interrupted), and notification `tag` for same-turn replacement without re-alert. Recheck eligibility before display; if verification fails, fail closed. Do not use `tag` alone as a durable guarantee or replace alerts for different turns/rooms. A cleared site store/reinstall, provider redelivery, OS notification behavior, and in-flight off/sign-out races prevent a literal across-all-devices exactly-once guarantee; test and describe this limit in the handoff. [RFC 8030 delivery acceptance/retries](https://www.rfc-editor.org/rfc/rfc8030#section-5) · [Push API delivery/ack](https://www.w3.org/TR/push-api/#receiving-a-push-message) · [notification `tag`](https://notifications.spec.whatwg.org/#dom-notificationoptions-tag) · [turn decision](../issues/02-turn-boundaries.md)

## Revocation and private routing

- Off: D1 write switches off and deletes all subscriptions (atomic D1 batch); sign-out: revoke this install's registration **before** auth sign-out when possible and bind rows to the auth session so failed cleanup cannot continue delivery; deletion: mark `accountDeletion` first and remove preference/registrations in `beforeDelete` (with retryable cleanup), then reject all subsequent sends for that user. Expiry must explicitly delete a room's alarm before its existing `deleteAll()`: this Worker's 2025 compatibility date predates automatic alarm deletion. Current `beforeDelete` sets the marker and redacts room data, while the frontend sign-out is a bare `authClient.signOut()`; neither path currently handles push. Revocation cannot recall a push already accepted by a provider; SW revalidation should suppress it where the platform permits. - Send encrypted minimal payload `{turnId, roomId, recipientId, enrollment generation}`; visible notification **only** “It’s your turn”. Validate IDs against persisted server state; the SW contacts only the configured API origin with credentials and `cache: 'no-store'`, never follows a supplied URL. Before showing, server verifies the current auth session's user is the recipient, preference/enrollment active, current turn/player, and presence. On click, compare the current signed-in identity again: if different/missing, open a neutral account-gated entry (do **not** load `/room/<id>` under the other account); after original-player sign-in, navigate the validated same-origin `/room/<id>`. Focus that room's existing client or open a new one; missing room uses Lobby link. The current room route would show a room to _any signed-in user_ via `getRoomView` and cannot enforce original-recipient routing by itself. ## Blocking platform conflict / recommendation

**Cannot promise both strict pre-display stale/presence suppression and supported classic Web Push on WebKit.** WebKit explicitly requires a user-visible notification for _every delivered push_ and says silent suppression can revoke the subscription. The agreed policy requires suppressing an alert on receipt if turn/presence/auth cannot be confirmed; network failure, a newly focused room, or a turn ending after the server sends makes that inevitable sometimes. A short TTL and pre-send check narrow but cannot eliminate this race; declarative push would display without the SW check. **Recommend prioritizing privacy/stale suppression and treating WebKit/iOS delivery as conditional until real-device tests establish that occasional deliberately dropped stale events do not revoke subscriptions.** If revocation occurs, the human must explicitly relax pre-display suppression for WebKit (or remove that platform from supported delivery); do not silently change either prior decision.
