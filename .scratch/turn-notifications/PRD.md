# Turn notifications for online rooms — implementation spec

Status: ready-for-agent

## Problem Statement

A seated Player can miss a new Turn when they are away from an online room. The live table shows whose Turn it is, but a Player with the room in another tab, on another device, or closed has no opt-in alert. An alert must not imply a Turn is still waiting after it ends, expose room or hand details on a lock screen, or deliver under the wrong account. Browser, Android Trusted Web Activity (TWA), and WebKit push capabilities and validation requirements differ.

## Solution

Offer an account-wide, off-by-default Turn notification switch in online-room Table settings for signed-in seated Players. Consent alone does not enable a device: the Player explicitly enrolls each capable browser/app install. On a distinct new Turn, alert each enrolled install at most once when no device is actively viewing that room, subject to checks at Turn start, send, and receipt. Display only **“It’s your turn”** and take a tap to the intended Player's current room, with sign-in and missing-room handling. Keep the live room experience working without push and treat delivery as best-effort. Release web support against real-push checks; handle Android TWA device testing as manual follow-up and gate the two WebKit surfaces separately.

## User Stories

1. As a signed-in Player seated in an online room, I want a Turn notification switch in Table settings, so that I can choose whether to receive alerts across my online rooms.
2. As a Player, I want the switch off by default, so that no alert is sent without my consent.
3. As a Player, I want the account switch to be distinct from device setup, so that turning it on does not unexpectedly request permission or imply this device is ready.
4. As a Player, I want to enroll an install with an explicit **Enable on this device** action, so that each device participates only when I choose.
5. As a Player with multiple devices, I want the switch to stay consistent between rooms and devices, so that my consent has one meaning everywhere.
6. As a Player, I want the device card to distinguish Not enabled, Ready, Blocked, Unavailable, and retryable setup failure, so that I know what to do next without confusing permission with delivery.
7. As a Player who denied or revoked permission, I want instructions rather than repeated automatic prompts, so that I can change browser/OS settings deliberately.
8. As a Player in an ordinary iOS browser tab, I want to learn that Home Screen installation is required, so that I do not attempt unsupported enrollment.
9. As a Player, I want to remove one install without changing account consent or other devices, so that I can manage enrollment individually.
10. As a Player, I want turning the switch off to stop all my enrolled installs and require fresh enrollment if I turn it back on, so that previous registrations cannot silently return.
11. As a Player signing out or changing accounts on an install, I want that install detached from the old account and never inherited by the next account, so that alerts do not cross identities.
12. As a Player deleting my account, I want pending alerts stopped and registrations removed, so that deleted identity data is not used for delivery.
13. As a Player whose first Turn starts after a deal, I want an alert when away, so that I know play has begun.
14. As a Player whose Turn starts after a play or pass, I want a new alert when away, so that I know it is time to act.
15. As a Player who regains the lead after the final pass, I want that distinct Turn recognized even if I was the last Player to play, so that it is not mistaken for my old Turn.
16. As a Player in a newly dealt game, I want a fresh Turn recognized even if the same Player starts, so that the new game is not missed.
17. As a Player, I want rejected actions, repeated snapshots, reconnections, resets, game end, and winning plays not to create false alerts, so that only real ongoing Turns notify me.
18. As a Player, I want no repeated reminder for an unchanged Turn and no backfill when I opt in or enroll mid-Turn, so that alerts correspond to new opportunities only.
19. As a Player actively viewing the relevant room on any device, I want all my installs quiet for that Turn, so that I am not interrupted while playing.
20. As a Player viewing the Lobby or a different room, or with the intended room unfocused/backgrounded, I want to remain eligible, so that an open tab or connection does not mask a Turn.
21. As a Player who was watching at Turn start and leaves later, I want no delayed alert for that Turn, so that leaving does not create a reminder.
22. As a Player who opens the room before a queued alert is sent or displayed, I want that alert suppressed, so that it does not arrive unnecessarily.
23. As a Player with two enrolled installs, I want each eligible install to receive at most one alert for a Turn, so that I can notice it on either without duplicates on one.
24. As a Player seated in multiple rooms, I want each alert to return to its intended room, so that generic notification text does not lead me to the wrong table.
25. As a Player, I want only generic visible alert text, so that the lock screen does not disclose my room, identity, cards, or destination.
26. As a Player tapping an alert, I want an existing view of the intended room focused if possible, otherwise a new view, so that another room is not replaced.
27. As a Player who taps after the Turn or game ends, I want to see the room's current state, so that the alert does not resurrect old play.
28. As a Player tapping after the room expires, I want **“This room could not be found”** and **Return to lobby**, so that I have a clear way forward.
29. As a Player who signed out, or whose device now has another account, I want to sign in as the original Player before the room is revealed, so that the alert does not bypass account boundaries.
30. As a Player, I want a failed or delayed push to leave the accepted game action intact, so that notifications never interrupt play.
31. As a keyboard or screen-reader user, I want distinct accessible controls, visible state and errors, and announced asynchronous results, so that setup and recovery are usable without sight or a pointer.
32. As a Player on a supported web browser, I want a real-delivery-tested experience while understanding that Ready does not guarantee OS delivery, so that the product does not overpromise.
33. As a Player using the Android TWA, I want enrollment only when delegation, permission, subscription, and registration actually work, so that an incapable build does not claim Ready.
34. As a Player using macOS Safari or an installed iOS/iPadOS Home Screen app, I want enrollment only after that surface passes its own real-device suppression and follow-up-delivery checks, so that a failing WebKit surface does not claim support.

## Implementation Decisions

- **Authoritative Turn:** The online room Durable Object recognizes accepted deal, play, and pass transitions that leave an ongoing game with a seated Player to act. A final pass returning the lead to the same Player and a newly dealt game create new identities. Persist a stable room/game-scoped Turn occurrence and recipient with game state; never derive alerts from snapshots or the current Player index alone. Invalid/no-op actions, restore, re-entry, reset, winning play, and game end create no new Turn; ending a Turn retires its pending work. Preserve the existing room-expiration policy for inactive rooms, including unfinished games.
- **Presence and timing:** Maintain short-lived, affirmative, room-scoped visible-**and**-focused presence for authenticated Player views across tabs/devices. The room socket count is not evidence of focus. Expired/missing evidence means away. Check at Turn start; if actively viewing, create no intent and never backfill. If away, recheck before each send and at receipt; a later skipped alert does not become a reminder. A different room, Lobby, background/unfocused tab, or disconnected view does not suppress. No claim to recall an OS notification after display.
- **Consent and enrollment:** Store an off-by-default account preference and per-install, session-bound registrations in the account database, apart from room state. Only signed-in seated Players see the switch in online-room Table settings, not Spectators or offline tables; use the agreed layout A (switch plus separate **this device** card, alongside sound). Toggling on persists consent without permission prompting or subscription. An explicit tap starts permission/subscription/server registration. Consent and enrollment must predate the Turn. A successful setup requires all three for Ready; permission alone is insufficient and Ready is not proof of actual delivery. Provide individual removal, retryable failures, denied/revoked and unsupported states, and no automatic permission reprompt. Do not claim an off switch revokes OS permission.
- **Revocation and identity:** Turning off removes all account registrations and invalidates the enrollment generation; re-on requires new per-install taps. On sign-out detach this install, bind registrations to a live session for race-safe ineligibility, and never transfer or auto-reenroll an origin subscription on any account's sign-in. Account deletion prevents sends and removes registrations. Enrollment endpoints require authentication, reject deletion or off states, prevent silent transfer of an endpoint between accounts, validate provider endpoints and input sizes, and do not expose subscription secrets in responses or logs.
- **Delivery and reliability:** Use VAPID Web Push through the existing root-scoped offline service worker, with the private key only on the backend; no separate native FCM path by default. In the room Durable Object, commit a new Turn identity and (only if away at start) a bounded outbox intent in the same local transaction as accepted game state. Drain via alarm, with bounded work, short TTL/deadline and retries, and a periodic repair path that wakes stranded persisted intents without inventing Turns. Before each send, verify the current Turn, seat/recipient, non-expiring room, fresh presence, account consent, enrollment generation, live originating session, and no account deletion. Persist per-Turn/per-install progress and retire invalid endpoints; distinguish retryable provider failures from permanent ones. D1/network/push/alarm failures after commit must not turn a successful game action into a failed one. Provider acceptance is not device display and literal exactly-once is impossible across network and OS failures.
- **Receipt and privacy:** Send only encrypted, validated identifiers needed for current-Turn verification and routing, never a client-supplied URL or visible room/game details. Before display, the service worker uses a non-cached authenticated server check for the current Turn, intended recipient/session, registration and consent, room, and fresh presence. Failure, unavailable verification, another signed-in account, or stale Turn means **show nothing**, including on WebKit; no visible fallback or declarative bypass. Persist device-side per-Turn deduplication and avoid replacing alerts for distinct Turns/rooms. Show only **“It’s your turn”** when verified; revalidate or gate identity again on tap.
- **Tap and return:** Focus a client already showing the intended room if possible; otherwise open a new client rather than replacing another room. A missing or different current account enters a neutral original-Player sign-in gate before exposing/opening the validated same-origin room path. Then load current room state even if the Turn/game has ended. If the room no longer exists, show **“This room could not be found”** with **Return to lobby**.
- **Device UX:** Persisted switch saves and completed enrollment have success feedback; failed saves cannot appear on or Ready. Show Not enabled before setup, Blocked for denied/revoked permission, Unavailable for actual lack of capability, and an error with retry for subscription/registration failure. Explain Home Screen installation in ordinary iOS tabs; they cannot enroll. Use separate labeled keyboard-operable controls, visible focus, text (not color alone) for state/errors, polite announcements, and normal dialog focus management. Do not prompt on load, settings open, or switch toggle.
- **Android TWA:** Implement notification delegation in the generated wrapper, Android 13+ notification declaration/runtime permission, and valid app links/signing; inspect the merged manifest. An actually non-delegated or failing build is not Ready. Once the capable setup completes permission, subscription, and registration, allow enrollment and Ready **without requiring prior physical-device delivery verification**. Manual sideloaded and Play-installed device testing follows; it is not a web-release or enrollment gate. This supersedes the earlier unverified-build enrollment gate in the settings/platform investigations, not the WebKit gates.
- **WebKit:** macOS Safari and installed iOS/iPadOS Home Screen PWAs are independent conditional enrollment surfaces. Withhold each as Unavailable until its own physical-device real-push gate passes, including receipt-time suppression and follow-up delivery after suppressed pushes and restart. If suppression displays an alert, subscription is revoked, verification fails, or another gate fails, withhold that surface; do not weaken fail-closed behavior or substitute a visible fallback. A pass supports only the tested surface/version, not perpetual delivery.

## Testing Decisions

- Test externally observable behavior, not helper calls, implementation-specific timers, or a simulated push alone. Prefer the highest existing seams: the room Durable Object's accepted game actions and persisted/reloaded state for Turn/outbox/presence; authenticated backend APIs with the account database for consent, enrollment and verification; service-worker push/click events plus room settings and navigation for receipt, deduplication, accessibility and return. Exercise failure injection at these boundaries. Existing game-state-machine lifecycle tests, room Durable Object leave/expiry tests, authenticated room API tests, room-route auth/rejoin tests, and GameRoom component tests are prior art. Focus behavior assertions on transitions and outcomes; use lower-level tests only for behavior inaccessible at those boundaries.
- Deterministic automated tests cover the following scenarios (including concurrency, restoration and duplicate receipt where possible):

| Area                    | Given / when                                                                                                                | Expected observation                                                                                                                                                             |
| ----------------------- | --------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Turn boundary           | Accepted deal, valid play/pass, final pass returning the lead, or fresh deal with same starter                              | Each new ongoing Turn has a distinct persistent identity; no more than one intended/displayed alert per enrolled install per Turn where platform permits.                        |
| No false Turn           | Rejected action, duplicate snapshot, re-entry, restored room, reset, winning play, or game end                              | No new alert; work for ended Turns retires.                                                                                                                                      |
| Cross-device focus      | Laptop visibly focused on this room at Turn start, phone enrolled; laptop later backgrounds                                 | Neither device alerts for that Turn, including after backgrounding.                                                                                                              |
| Away and race           | Laptop in Lobby, another room, or unfocused/backgrounded room; phone enrolled; Player focuses this room before send/receipt | Away at start permits intent; later focus suppresses all pending alerts. Missing/expired presence means away; already displayed alerts need not be recalled.                     |
| Multiple rooms/devices  | Player seated in A and B, focused on B, with two enrolled installs                                                          | A may alert once per install; B focus does not suppress A; each alert keeps its room and distinct Turns do not overwrite one another.                                            |
| Opt-in timing           | Default off; switch on; enroll one install during an existing Turn                                                          | No prompt on toggle, no mid-Turn backfill, other install remains Not enabled; next eligible Turn may alert.                                                                      |
| Device states           | Permission denied/revoked, unsupported API, subscription/server failure, successful retry                                   | Blocked/Unavailable/retryable state as appropriate, never false Ready or automatic reprompt; other devices and consent unchanged.                                                |
| Revocation and identity | Remove one install, turn off/re-on, sign out/in, change account, or delete account with queued work                         | Removed registrations ineligible at send/receipt, re-enrollment explicit, no cross-account transfer; displayed alert tapped under another account gates original-Player sign-in. |
| Delay and failures      | Provider delays/duplicates, device offline, receipt check unavailable, Turn ends, endpoint invalid                          | Suppress stale/unverifiable alert; bounded eligible retries and persistent device dedupe, retire invalid endpoint, no catch-up reminder or promised offline receipt.             |
| Navigation              | Tap after Turn/game ended, room expired, same-room client open, only different-room client open                             | Current room state or missing-room text and Lobby link; focus same room or open new, without exposing target to other account or arbitrary URL.                                  |
| Game safety             | Provider/auth/config failure, alarm repair, or database failure after game commit                                           | Accepted action stays successful; persisted intent retries within bounds or expires, and repair never invents a Turn from a snapshot.                                            |
| Accessibility           | Keyboard/screen-reader settings operation and async save/setup outcomes                                                     | Labeled separate switch/action, visible focus and textual state, usable dialog focus, announced success/errors.                                                                  |

- **Web release gate:** On a real HTTPS deployment, send actual VAPID push to subscribed endpoints on **Chrome or Edge desktop, Firefox desktop, and Chrome on Android**. On each, test fresh permission/enrollment, a new Turn away from the room, receipt with tab/app closed or backgrounded, tap-to-room, foreground suppression, stale suppression, off/sign-out, and a subsequent eligible Turn. Record browser/OS versions, real-push outcomes and limitations. DevTools simulated service-worker events do not establish delivery. Browser/OS denial still uses the device-state fallback. **Do not wait for a physical Android TWA device test to release the web feature.**
- **Android manual follow-up:** After TWA delegation, OS permission, links/signing, and merged-manifest work, the developer manually checks sideloaded and Play-installed builds for allow/deny, browser permission, real delivery, attribution, cold/warm taps, account routing, and delivery after restart; raise issues for failures. Neither this physical-device test nor its outcome blocks capable-device enrollment or the web-release gate. Ready must never be described as proof of delivery.
- **Separate WebKit gates:** Test macOS Safari and installed iOS/iPadOS Home Screen PWAs independently on physical devices, with actual delivered pushes to the service worker (not DevTools emulation). For **each** surface, verify no alert for a stale Turn, focused room, different signed-in account, and unavailable verification; then verify a fresh eligible alert, retained usable permission/subscription, and correct tap. Repeat after browser/app restart, record OS/browser versions and retention, and check normal enrollment plus original-Player gating on a notification already displayed before account change. Withhold enrollment for a surface that cannot pass; passing one does not unlock the other. Ordinary iOS tabs remain unavailable.
- Push-service 2xx acceptance is not receipt/display. OS/network delays, lost responses, reinstalls and post-display focus races prevent absolute silence or exactly-once guarantees; unavailable receipt verification suppresses rather than displays. Record real-device results during implementation, not as achievements of this spec.

## Out of Scope

- Production implementation or physical-device testing in this planning effort.
- Solo, pass-and-play, Spectator, invitation, Room chat, or reminder notifications; repeated alerts for an unchanged Turn.
- A separate native iOS app, default native FCM path, guaranteed delivery on unsupported browsers, or an automatic catch-up alert after an offline period.
- Weakening fail-closed receipt suppression for WebKit, showing a generic fallback on a suppressed push, or treating an OS notification already displayed as recallable.
