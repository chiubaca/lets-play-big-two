# Turn notifications for online rooms — implementation handoff

## Outcome and boundaries

Offer opt-in Web Push when a seated Player's **new Turn** starts in an online room they are not **actively viewing**. The switch applies to the account across online rooms; each browser/app install requires its own explicit enrollment. The feature supplements, never replaces, the live room UI. No solo, pass-and-play, Spectator, invitation, chat, or reminder alerts. This is a planning handoff, not evidence of implementation or device testing.

The linked decision tickets are authoritative for detail: [turn identity](issues/02-turn-boundaries.md), [presence](issues/03-away-presence.md), [settings](issues/04-settings-and-permission.md), [content and return](issues/05-alert-content-and-return.md), [delivery](issues/06-delivery-design.md), [WebKit policy](issues/08-webkit-stale-push-policy.md), and [acceptance/release decision](issues/07-handoff-spec.md). Platform and delivery investigations: [push support](research/push-platform-support.md), [delivery design](research/delivery-design.md). Use the domain terms in [CONTEXT.md](../../CONTEXT.md).

## Required behavior

1. **Turn eligibility:** Only an accepted online deal, play, or pass that leaves an ongoing game with a Player to act begins a distinct Turn. A final pass returning the lead to the same Player and a new deal both create new Turn identities. Rejected actions, repeated snapshots, reconnects, resets, game end, and a winning play do not create an alert. A new Turn identity persists across room reloads. At most one displayed alert per enrolled device per Turn; no reminder for an unchanged Turn.
2. **Away at Turn start:** A visible **and** focused view of that specific room on any of the Player's devices suppresses alerts on all devices. A background/unfocused tab, another room, Lobby, disconnected tab, or mere open socket does not. Presence requires fresh affirmative room-scoped evidence; missing/expired evidence counts as away. If present at Turn start, never backfill that Turn after the Player leaves. If away at start, recheck presence and all other eligibility immediately before send and before display; a skipped alert is not retried as a reminder after presence returns to away. Races after display need not recall an OS notification.
3. **Consent and setup:** Off by default. Only signed-in seated Players see the switch in online-room Table settings; do not show it offline or to Spectators. Use [settings layout A](prototype/settings-flow.html?variant=A): account switch plus separate **this device** card. Turning on saves account consent only. A distinct **Enable on this device** tap requests permission and enrolls that install for the signed-in account; never prompt on page load, settings open, or switch toggle. Consent and enrollment must predate the Turn; enabling mid-Turn does not alert for it. **Ready** means permission, Web Push subscription, and server registration succeeded, not that real delivery is guaranteed. Support individual device removal. Off deletes all of that account's server registrations, without claiming to revoke OS permission; re-on requires fresh enrollment. Sign-out detaches this install and never transfers its origin-level subscription to another account or automatically reenrolls the same account on return. Account deletion prevents sends and removes registrations.
4. **Device states:** Show **Not enabled** before setup, **Ready** only after successful setup, **Blocked** for denied/revoked permission, **Unavailable** where the browser/app actually lacks the capability, and a retryable failure for subscription/server-enrollment errors. A denied prompt must not be repeated automatically. Explain Home Screen installation for ordinary iOS browser tabs. A non-delegated Android TWA build cannot claim it supports notifications; once delegation/permission/subscription support is implemented, it may offer enrollment without first passing a physical-device delivery gate. Android manual testing is follow-up, not a web-release prerequisite. Use success/error text, labeled keyboard-operable controls, visible focus, and polite asynchronous announcements; do not infer Ready from permission alone.
5. **Delivery:** Use VAPID Web Push in the existing root-scoped service worker; keep the private key on the backend. Store account preference and session-bound per-install registrations in D1. The room Durable Object commits a new Turn identity and an away-at-start outbox intent atomically with successful game state; its alarm drains bounded work, with a repair path for stranded persisted intents. At each send, check the current Turn, seat/recipient, room, fresh presence, consent, enrollment generation, session, and account deletion. Use short TTLs and bounded retries, retiring invalid subscriptions. Keep per-Turn/per-install progress and persistent service-worker deduplication. Push-service acceptance is not device display, and exactly-once delivery cannot be guaranteed across network failures, reinstalls, and OS behavior. A push outage or subscription failure must not turn a committed deal/play/pass into a failed game action.
6. **Receipt and privacy:** Before display, revalidate Turn, recipient, consent, enrollment, session and presence via a non-cached authenticated server check. If the check fails, is unavailable, or the Turn is stale, show nothing. A notification displays only **“It’s your turn”**; no room name/code, Player name, cards or URL in visible copy. Payload/notification data contains only validated identifiers, never a client-supplied navigation URL. A notification already displayed need not be recalled when state changes.
7. **Tap:** Focus an existing client showing the intended room if possible; otherwise open a new client without replacing another room. Require the original Player to sign in if signed out or if another account is now active, before revealing/opening the target room; then navigate to the validated same-origin room path. Open current room state even if the Turn or game ended after display. If the room is gone, show **“This room could not be found”** and a **Return to lobby** link.

Run deterministic unit/integration tests for the transitions and eligibility checks; use real endpoints and physical devices for the release checks below. A service-worker event simulated in DevTools alone does not establish delivery.

## Validation and release boundaries

- **Web release gate:** Use a real HTTPS deployment and actual VAPID send to a subscribed endpoint on **Chrome or Edge desktop, Firefox desktop, and Chrome on Android**. Exercise a fresh permission/enrollment, a new Turn with room unfocused, receipt with tab/app closed or backgrounded, tap-to-room, foreground suppression, stale suppression, off/sign-out, and a follow-up eligible Turn. Test the acceptance table in automated integration/unit coverage where practical; record browser/OS versions, real-push outcome, and any limitations. Browser-specific API/OS denial still uses the device-state fallback. This web gate does **not** wait for an Android TWA device test.
- **Android TWA:** Implement notification delegation in the generated wrapper, Android 13+ `POST_NOTIFICATIONS` declaration/runtime permission, and valid app links/signing. Inspect the merged manifest. Do not mark an unsupported or failed setup Ready, but **do not withhold enrollment or web release merely because TWA end-to-end receipt has not been manually verified**. The developer will manually test sideloaded and Play-installed builds, OS allow/deny, browser permission, real delivery, notification attribution, cold/warm tap, account routing, and after-restart delivery; raise issues for failures. This replaces the earlier unverified-TWA enrollment gate in [settings](issues/04-settings-and-permission.md) and the research recommendation in [push support](issues/01-supported-delivery.md). Do not claim Android delivery is proven merely from Ready state.
- **WebKit surfaces:** macOS Safari and installed iOS/iPadOS Home Screen PWAs are **separate conditional enrollments**. Keep each unavailable until a physical-device real-push test verifies suppression for stale Turn, focused room, different signed-in account, and unavailable verification, followed by a fresh eligible alert and tap. Repeat after browser/app restart; record OS/browser versions and subscription retention. If a suppressed push shows an alert, the subscription is revoked, or end-to-end verification fails, withhold that surface; do not substitute a visible fallback. Ordinary iOS browser tabs cannot enroll.
- **Limits:** A Web Push service's 2xx acceptance does not prove receipt. Network/OS delays and focus races after an alert is displayed prevent absolute silence or exactly-once guarantees. A failed/no-connection receipt verification suppresses the alert rather than showing potentially stale or private information. Real-device results are recorded during implementation, not asserted by this handoff.

## Implementation entry points

- `packages/game-state-machine/src/game-state-machine.ts` (accepted transitions), `apps/backend/src/do/big-two-room-do.ts` (turn persistence, presence, outbox and alarms), `apps/backend/src/hono/app.ts` and `packages/data-ops/src/drizzle/schema.ts` (authenticated enrollment/eligibility, D1); preserve [room expiration](../../docs/adr/0001-expire-unattended-rooms-and-chat.md).
- `apps/frontend-web/public/service-worker.js` (augment the existing offline worker with push/click handlers), `apps/frontend-web/src/components/game-room/game-room.tsx` (online Table settings), `apps/frontend-web/src/routes/room/$roomId.tsx` (account-gated return and missing room).
- `apps/android/twa-manifest.json`, generated Android manifest/build, `apps/frontend-web/public/.well-known/assetlinks.json` (TWA delegation, permissions and verified links). Do not create a separate native FCM path by default.
