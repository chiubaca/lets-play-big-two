# Live-only room chat — implementation handoff

## Scope and language

Add room chat to **online** Big Two rooms only. A **Player** occupies a current room seat and can send; a signed-in **Spectator** can read but cannot send. Room chat is available while waiting, playing, and after a game. It is room-scoped, not game-scoped: an open tab keeps its chat log, unread count, and draft when another game starts in that room. It is **live-only**: no history for late arrivals, refreshes, or disconnected periods.

The resolved decisions are the authority for details: [chat surface](issues/01-chat-surface.md), [delivery](issues/02-live-delivery.md), [authorization](issues/03-chat-authorization.md), and [finished-room access](issues/05-finished-chat-access.md). The [approved UI prototype](../../apps/frontend-web/src/components/game-room/room-chat-prototype.tsx) is a visual reference only: its seeded messages, local reply, single-line 280-character input, and always-live log are **not** production requirements. This spec adds acceptance scenarios and integration guidance without implementing them.

## Interaction

- Put a circular, gold-trimmed chat trigger immediately after the online room menu and before the spectator count. Closed by default; show the number of unread messages, not just a color cue. Opening clears the count. Incoming messages while closed increment it, including while another modal makes chat inaccessible. A message received while open stays visible and scrolls the independently scrolling log to the newest entry; a successful local send does too.
- Open a compact panel under the header. On narrow screens, move the room code into a short second header row and anchor the panel below it. The panel must not obscure the room code or table controls. Show literal author/message text; a Player gets a composer and Send button, a Spectator gets a read-only explanation. When a Player loses a seat, switch to read-only but retain that tab's unsent draft for a possible later return to a seat; the server denies any stale attempted send in the meantime.
- The trigger has an accessible name, expanded state, and unread count. The log is labelled and keyboard navigable. Opening/closing works from keyboard; Escape closes, visible focus remains, and closing returns focus to the trigger. While closed, announce an updated unread **count**, not the contents of every incoming message, so turns and card selection are not interrupted. Do not mount an active live message log while the panel is closed. Avoid duplicate spoken announcements for an HTTP acknowledgement and its socket echo.
- A tab that witnesses a transition to `GAME_END` gets a dismissible result modal; a late join or refresh into a finished room does not automatically open it. Modal focus stays inside and makes underlying chat inert. Dismiss via close control or Escape, restore focus to the persistent **Results** control, then allow access to chat. A compact finished-room strip shows the winner, Results, Return home, and host-only Play again; Spectators see that the room awaits the host. Strip/actions wrap on small screens without blocking chat or game controls. Starting a new game closes the old result and removes the strip without clearing chat. A failed restart keeps the finished view. Reopening/dismissing Results leaves the chat log, unread count, and draft intact.
- If the chat socket disconnects but the game remains available, keep the existing chat log readable and the draft intact. Show a **chat-only** reconnecting status, not a game outage. An explicit HTTP send may still be attempted; success and failure must reflect the HTTP result, never the socket's status alone. A failed or unconfirmed send retains its draft and offers an explicit retry; do not display an unconfirmed message as sent. A successful send may be shown locally even when the author's socket is down.

## Delivery contract

- Use a separate room-chat Durable Object and receive-only chat WebSocket. An authenticated HTTP endpoint accepts sends and forwards accepted messages to the chat object. Do not put chat in the game-state machine or send it through the game's read-only socket. Open one chat socket per open online room tab even with the panel closed. Every currently connected, authorized tab (including the sender's other tabs) receives each accepted message. Game spectator presence/count must not count chat sockets.
- Each tab keeps its own in-memory log and unread count. A new tab, refresh, or re-entry starts empty; do not fetch or replay history. After disconnect, reconnect, Android Trusted Web Activity background/resume, or suspended network, only subsequent live messages arrive. Retain already displayed messages locally unless refreshing/leaving or redaction reconciliation requires clearing them; never invent missed entries or fill sequence gaps.
- Assign accepted messages a room-local order and message ID. Connected tabs display accepted messages in that order; no gap-fill endpoint. HTTP acknowledgement and WebSocket event carry matching identity/order information so the sender merges a confirmation and echo into one displayed entry. Do not enqueue automatic resends. A client-generated send ID is reused on manual retry; deduplicate accepted retries for 10 minutes, including across chat-object hibernation/restart. Retain only bounded acknowledgement/deduplication metadata and sequence bookkeeping, never replayable message bodies. After 10 minutes an unresolved send cannot claim exactly-once retry: explain the uncertainty and require a new explicit submission. A reused ID with different text must not silently acknowledge an earlier message.
- Chat and game connections have independent lifecycles. Chat failure must not stop game updates or make game actions fail; a game-socket reconnect must not cause chat history replay or count chat watchers as game Spectators.

## Authorization and input contract

- On socket admission, send, and continuing delivery, require a current signed-in session with no pending deletion, a valid online room record, and live room state. Any eligible room visitor may read, seated or not; D1 `usersToRooms` is not a read requirement or seating authority. The same eligibility applies in all three room phases. If the room record/live state disappears, reject new connections/sends and close existing chat sockets promptly.
- Resolve a current seat from authoritative room state **for every send and retry** and match its account ID to the authenticated sender. Ignore claimed client author, role, room phase, name, or stale UI. Attach the seat's stored display name at acceptance. A Spectator gaining a seat may send; a Player losing one cannot, even before their UI updates. Invalid sessions and deletion-pending accounts stop receiving and cannot send; close their sockets promptly, not only on initial upgrade.
- When an account is deleted, push a live redaction that relabels its already-delivered entries in connected tabs **Deleted player**, using an opaque author correlation key rather than exposing account IDs. A suspended/disconnected tab must reconcile deletion status for authors in its in-memory log before showing that log again, or clear the old log; never fetch chat history. Previously seen or copied text is not retroactively erased.
- Accept only structured plain-text message text and client send ID. Trim outer whitespace; reject empty text, more than **200 grapheme clusters after trim**, more than **three lines**, other control characters, over **4 KiB UTF-8 text**, or over **8 KiB entire request body**, with actionable feedback. Never truncate. Render literally, without HTML, Markdown, or clickable links. On rejection keep the draft. No chat-specific rate limit, mute, report, or moderation UI in this release; normal authenticated endpoint protections still apply.

## Acceptance scenarios

1. **Phase and role matrix:** In waiting, active play, and finished room, a seated Player opens chat, reads and sends; a signed-in Spectator opens the same conversation but cannot compose or submit, including by direct HTTP. A signed-out/deletion-pending visitor cannot connect or send. Joining a seat enables compose; losing it switches to read-only without discarding the draft, and a direct send is denied immediately.
2. **Live audience:** With chat closed in one tab and open in another, an accepted send appears once in both and in every other currently connected authorized tab in room order. Only the closed tab gains an unread count; opening clears it. Two tabs of the same author each receive the message. A late join, fresh tab, and refreshed tab start with empty logs. Opening the panel does not trigger history fetch.
3. **Send uncertainty:** When HTTP succeeds but the sender's socket is down, show one confirmed local message, clear the draft, and do not await echo. When HTTP fails or the result is unknown, keep the draft and show a manual retry; do not optimistically present it as delivered. A late echo plus acknowledgement yields one entry. Retrying the same send ID within 10 minutes does not fan out twice; a changed payload under the same ID is rejected. Outside the window, explain uncertainty and require a new explicit submission, not an automatic retry.
4. **Independent outages:** Drop chat while game remains connected: game turn updates and actions still function, the log remains readable, chat-only reconnecting status appears, draft remains, and an explicit HTTP send can succeed or fail independently. Drop/reconnect the game socket while chat remains connected: live chat still works; game spectator count is unaffected by chat sockets. On chat reconnect, no messages missed while disconnected appear and no gap filling occurs.
5. **Android/background:** In the Trusted Web Activity, background/suspend and foreground/resume reconnect chat independently of game state. Already displayed messages remain in that tab where still in memory; messages missed while suspended do not replay. If deletion occurred during suspension, reconcile or clear old chat **before** rendering it on resume. A fresh process/refresh starts empty.
6. **Finished room:** A tab witnessing game end sees the result modal and can dismiss it to reach chat; refresh/late join sees the persistent result strip instead. Results reopens with proper modal focus; Escape/close restores focus to Results. Host can Play again from the strip; non-host Player and Spectator cannot restart, and all may Return home. Chat state survives modal open/close and restart; a failed restart does not strand anyone. Narrow layouts preserve chat, code, and controls.
7. **Input and safety:** Test blank/whitespace, exactly/over 200 graphemes (including emoji and combining marks), exactly/over three lines, disallowed controls, 4 KiB/8 KiB boundaries, malformed types, HTML/Markdown/URL-looking text, and Unicode names. Valid text renders literally; invalid input yields actionable error and retains draft. Account deletion redacts labels in connected tabs without revealing account IDs or storing message history. A room removed mid-session stops sends/delivery and closes sockets.
8. **Accessibility and scope:** Keyboard and touch can reach chat without hiding table actions; focus returns as specified, unread is exposed by count, and a closed chat does not read each message aloud. Repeated acknowledgements do not duplicate visible or spoken entries. Offline/solo/pass-and-play tables show no chat. Neither chat operations nor room restarts accidentally change game turns, private hands, or spectator presence.

Acceptance should include automated server tests for authorization, validation, deduplication, ordering, redaction, and room lifecycle; client tests for log/unread/focus/uncertain sends, role/phase changes, and reconnect; and a browser check of narrow-screen modal/chat interaction and foreground/resume behavior. The implementation effort may split this handoff into separate tickets; this map does not implement chat.
